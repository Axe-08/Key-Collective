## Step 1 Findings (Google Sign-In & Dashboard Initial Load)

### QA-01 — `Failed to fetch standing: 401` on Dashboard after Google Sign-In
- **Symptom:** Immediately after signing in with Google and completing the consent modal, the Standing Card displays `Failed to fetch standing: 401` with a `Retry` button.
- **Root Cause:**
  1. When `console-dev.key-col.axe08.tech` first loads before sign-in, `StandingCard.svelte` (`onMount`, lines 35–39) and `DashboardView.svelte` (`onMount`, lines 51–66) fire `GET /api/pool/standing` and `GET /api/pool/contribution` without a session cookie, receiving `401 Unauthorized`.
  2. When Google Sign-In + Consent completes (`POST /api/auth/google` → `POST /api/auth/consent`), `App.svelte` calls `refreshSession()`, which updates `userAccount` and calls `loadData()` (`/api/keys`, `/api/logs`, `/api/stats`), but **neither `StandingCard.svelte` nor `DashboardView.svelte` reacts to `userAccount.id` changing**, leaving `StandingCard` stuck on the pre-login `401` error until `Retry` or page reload.

### QA-02 — Sybil Trust Score hardcoded to `95/100` on Google Sign-In & Fake 5-Layer Trust Checks
- **Symptom:** A freshly signed-in Google user (with no GitHub linked) shows `95/100 TRUST (Low Risk • High Reputation)`, `GitHub Account Age: Verified (> 30d)`, and `Public Repositories & Activity: Active Contributor`.
- **Root Cause:**
  1. **Backend (`src/worker/router/dashboard/auth_routes.ts:66`):** `handleGoogleAuth` hardcodes `const sybilScore = 95;` and inserts `95` into `users.sybil_score` on first Google sign-in. Additionally, `src/worker/router/dashboard/handler.ts:279` falls back to `userRow.sybil_score ?? 95`. Real anti-Sybil scoring (`evaluateAntiSybil`) only runs during GitHub OAuth linking (`src/auth/github/link_flow.ts`).
  2. **Frontend (`ui/src/lib/workbench/IdentityCard.svelte:164-183`):** The 5-Layer Trust Checks derive their pass/fail status and labels (`Verified (> 30d)`, `Active Contributor`, `Clean Subnet • Dedicated`) purely from numeric thresholds on `sybilTrustScore` (`>= 20`, `>= 40`, `>= 60`, `>= 30`) without checking whether a GitHub identity actually exists.

### QA-03 — Email prefix shown as `@<githubUsername>` before linking GitHub (and `<> Local` badge)

## Step 2 Findings (Playground & `/v1/chat/completions`)

### QA-07 — Browser Playground fails with `NetworkError when attempting to fetch resource.` (CORS Preflight Block)
- **Symptom:** Clicking `Send Request` in the browser Playground (`https://console-dev.key-col.axe08.tech` → `https://api-dev.key-col.axe08.tech/v1/chat/completions`) immediately fails in the browser with `NetworkError when attempting to fetch resource.`, whereas running the generated `curl` command from the terminal reaches the Worker.
- **Root Cause:**
  1. `ui/src/lib/Playground.svelte:190-194` sends the custom header `'x-pool-fallback': 'lenient'` on a cross-origin request (`console-dev.*` → `api-dev.*`).
  2. `src/worker/gateway/types.ts:24-30` defines `CORS_HEADERS["access-control-allow-headers"]` as `"Content-Type, Authorization, x-tenant-id, x-kc-trace-id, x-trace-id"` — **`x-pool-fallback` is missing**, causing the browser to reject the CORS preflight response with a `NetworkError`.
  3. Additionally, `CORS_HEADERS` is missing `access-control-expose-headers: x-kc-cu, x-kc-model, x-kc-model-used, x-kc-provider, x-kc-request-id, x-kc-fallback`, so browser JS in `Playground.svelte:206,213` cannot read `res.headers.get('x-kc-cu')` or `res.headers.get('x-kc-model-used')` across origins.

### QA-08 — `FALLBACK_EXHAUSTED` returns `type: "internal_server_error"` when pool has 0 keys
- **Symptom:** Running the `curl` command against `https://api-dev.key-col.axe08.tech/v1/chat/completions` when `key-collective-d1-dev` has 0 keys returns `{"error":{"message":"Cascade routing exhausted all 2 candidate route(s) without success","type":"internal_server_error","code":"FALLBACK_EXHAUSTED"}}`.
- **Root Cause:**
  - There are currently `0` keys in `key-collective-d1-dev` (`Keys 0`), so both candidate routes in the cascade (`google` → `groq`) have no keys available to lease. Per `D.3.4`, the error `type` in the JSON body returns `"internal_server_error"` when no provider key is available instead of distinguishing pool/provider capacity exhaustion from an internal server fault.

### QA-12 — Adding a real Gemini key fails with `provider_unavailable` (`"The provider is not answering right now. Please retry in a minute."`)

### QA-13 — 3 uncreated `Project-Scoped API Keys` appear in Workbench associated with a non-existent `'Production Gateway'` project
- **Symptom:** The Workbench `Project-Scoped API Keys` table shows 3 keys (`API key …<6 chars>`) associated with project `Production Gateway`, even though the user has `0` projects and never created any project keys.

  3. **`GET /api/tokens` returns all non-expired `auth_tokens` rows:** `handleGetTokens` (`token_routes.ts:224`) returns all non-expired rows in `auth_tokens`, including `tok_play_%` and unscoped login tokens.
